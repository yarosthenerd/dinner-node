Run a node

Turn an idle GPU into a kitchen. Testnet only, so what you earn is MON with no monetary value.

Read this first. Guests send you their prompts in plaintext. You are running a machine that strangers type into, and on testnet you are doing it for play money. Do not run a node on a work machine, a machine holding anything sensitive, or a connection you do not control.

What you need

Start

git clone <repo> dinnernode
cd dinnernode
./dinnernode

That is the whole thing. It installs dependencies, runs setup, opens a tunnel if it can, and starts serving. Setup is idempotent, so you can run it as often as you like; it only writes what is missing and it never overwrites a key you already have.

On the first run it will:

  • check Node and Ollama, and tell you what to install if either is absent
  • measure your GPU, size every model you have against it, and default to the largest one that fits entirely in VRAM
  • generate a node wallet and save it to .env with owner-only permissions
  • offer to request testnet MON for it
  • register your node on chain so guests can find it

To check readiness without changing anything, run npm run doctor. It exits non-zero and prints what to fix if the node is not ready to serve.

What would I earn?

Read the two numbers that decide the answer before you read the answer.

  1. Utilisation. Not how fast your GPU is, but what fraction of the time it actually has a job. Today, on this network, that number is close to zero: there are two nodes and almost no demand. Everything below scales linearly with it, so a calculator that assumed 100% would be selling you something. The slider starts at 5%.
  2. MON has no monetary value. This is a testnet. Every dollar figure below is what the same work would be worth if MON traded at the modelling constant this project uses, and it does not trade at all. Your electricity bill is denominated in real money. Your earnings are not.

Where these numbers come from

Throughput is measured on one machine, and one machine is not a benchmark suite. Every row below was taken on 2026-08-27 with one model resident at a time, the model unloaded between runs, and the GPU/CPU split read from Ollama immediately afterwards. That last part matters: an earlier pass reported 27.7 tok/s for qwen3:8b and it turned out to be contention with a model the node had kept alive, not the model's speed.

The two rows that fit agree to within 10% on tok/s x weights, which is the evidence that decoding is bandwidth-bound and that scaling by model size is legitimate for models that fit. It is not legitimate for a model that spills: the two spilled rows above sit 9x apart on identical hardware. That is why the calculator refuses to extrapolate a spilled figure and shows the measured floor instead.

Prices are 90% of the median of every provider listing the same model on OpenRouter, read on 2026-08-27, which is the same band the live nodes price themselves against. Three catalog models (qwen3:1.7b, qwen2.5:3b, qwen3:4b) have no listing at all — nobody sells a model that small as an API — so the calculator shows no income for them rather than inventing one.

Two results worth knowing before you buy hardware

More VRAM is not monotonically more money. At 16 GB the picker moves you to qwen3:14b, which the market prices at roughly half what it pays for qwen3:8b while running about three times slower. On these figures a 16 GB card earns less than a 12 GB one. Check the calculator before assuming the bigger card pays for itself.

The mixture-of-experts model is the outlier. It needs 32 GB to hold, and in exchange it decodes at roughly the speed of a 3B model while being priced like a 35B one. It is also the least certain figure on this page: its active-weight size is derived, not measured, because no machine here can hold it. If you own a 32 GB card, measuring it is the single most useful thing you could contribute.

What it costs you to run

Be clear-eyed about this. On testnet the economics are not favourable and are not meant to be: the point is that the mechanism works, not that it pays.

  • Gas. Your node settles periodically during a job, and every settlement is a transaction whose gas you pay. At current testnet gas this costs more than the tokens earn. Keep an eye on your balance; a node that runs dry mid-job strands a guest's escrow and loses the work it had already done but not yet settled.
  • Electricity. A loaded consumer GPU draws a few hundred watts. Over a month of real use this is the larger number, and it is denominated in real money while your earnings are not.
  • Your machine, while it works. Set HOST_PRIORITY=owner (the default) and guests get throttled when you are using the machine yourself.

A note on VRAM, which is the whole game

Ollama does not refuse a model that is too large for your GPU. It loads what fits and runs the rest on the CPU, silently, and throughput collapses. This is the single most common way a node ends up earning nothing: it looks healthy, it is registered, and it is too slow for any guest to wait for.

Two things have to fit, not one:

need = weights + KV cache + about 0.6 GB of working buffers
KV cache = context x layers x kv_heads x (key + value width) x 2 bytes

The KV cache is not a rounding error. qwen3:8b is 4.9 GB of weights and 4.5 GB of KV cache at the default 32,768 context: sizing on the download size alone is out by nearly a factor of two, and that error is exactly what puts half your model on the CPU.

Setup does this arithmetic for you. It reads your VRAM, reads the layer geometry of each model you have installed from Ollama itself, and tells you which ones fit. If one is close, it offers to serve it at a smaller context rather than spilling. If none fit, it offers to pull one that does.

A bigger model that spills is worse than a smaller model that does not. On the reference laptop, a 27B on a 12 GB card runs 56% on the CPU and takes 84 seconds to produce its first token with the model already resident. Guests give up long before that.

What you are agreeing to

Running a node means handling other people's prompt text on your hardware. The Terms of Use section 5 sets out what that involves, and the Acceptable Use Policy covers what you may refuse to serve and how to report abuse. Both are short. Read them before you start, not after someone sends you something you would rather not have received.

You choose what your machine runs. Nothing in DinnerNode obliges you to serve any particular request, and you can stop your node at any time with Ctrl-C.

Stop with Ctrl-C, not Ctrl-Z. Ctrl-Z suspends the process and leaves it holding port 4173, so the next start fails with EADDRINUSE. If that happens, bring it back with fg and then Ctrl-C it.
